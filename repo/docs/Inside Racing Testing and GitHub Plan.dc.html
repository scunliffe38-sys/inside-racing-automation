The plan, in plain terms

Two jobs, done in a set order: give the code a proper home with a history, and prove the thing produces a correct edition from a month it has never seen. Neither is complicated, but they need doing in the right sequence, and a few of the steps are yours rather than mine.

1. What GitHub is for here

One thing only: a filing cabinet for the code that remembers every version. Every change is recorded with a date and a note, and any earlier state can be brought back exactly.

This is not theoretical. Earlier today one of my edits removed seven working pieces of the edition file at once, and putting it right meant reconstructing them by hand from other files. Under a repository that would have been a single command. As the system grows, the chance of that mattering goes up, not down.

Worth being clear about

GitHub holds the code. It does not hold the month’s files, and the production team never has to open it. Their world stays a folder and a shortcut. This step is about protecting the system, not about changing anybody’s job.

2. Starting personal, moving to RV later

Not a problem, and not something to wait for. Make the repository under your own account now and move it to RV when the corporate access exists. GitHub has a transfer function for exactly this: the repository keeps its whole history and every recorded change, and the address updates. Nothing has to be rebuilt or re-copied.

Two things to get right at the start, because they are awkward to change later. Make it private, so the code and any RV material in it are not public. And use an email address you will still have access to when the transfer happens.

3. What goes in, what stays out

One open question in section 6: the rebuild tests need a fixed set of inputs to run against, and those are exactly the files that should otherwise stay out.

4. Two tests, not one

These prove different things and fail in different ways, so they are worth keeping apart.

Content test
I run it, here
Does September’s data produce a correct edition — the right meetings, deadlines, folios and extent? You are holding back the published September PDF and giving me only the inputs, so I build it blind and you compare. That is a genuinely strong test: I cannot unconsciously work towards the answer. When it fails I can fix a parser and re-run in seconds.
Process test
You run it, on a real machine
Does someone dropping files in a folder and double-clicking get that same PDF out, with a readable check report beside it? I can write the runner but I cannot execute it — there is no Node, no command line and no headless browser available to me. The first time it truly runs will be on your machine.

The reason for this order: if the runner is built before September’s content is validated, the first run happens on your machine with both kinds of failure tangled together, and a wrong page becomes “is that the data, or the runner?”. One extra step separates them. I’ll also say plainly that the content test does not exercise the export path the runner uses, so some faults will only ever appear in the process test.
